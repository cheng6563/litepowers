# 代码即核心业务文档

**代码、日志和必要的就近注释共同构成核心业务信息。** 已实现的业务流程、规则、状态流转和约束以代码、SQL、schema、配置和测试为准；注释只补充代码无法直接表达的业务语义。日志不得包含敏感数据。

## 持久业务文档的最小边界

持久业务文档只保留代码、测试和少量就近注释仍无法充分表达的关键业务信息，例如跨多个模块的总体规则、边界或协作关系。文档应精简地说明这些不可由代码直接还原的信息，并指向相关代码；不要复述字段、调用顺序或局部实现规则。

如果一篇文档只剩业务概念或流程到代码入口的引用、没有独立业务价值，则不保留它。项目没有文档体系时，不要为记录业务信息新建持久文档目录、模板或治理体系；直接让代码和必要的就近注释承载信息。

稳定项目约定、面向外部读者的使用说明、集成协议、运维手册或合规记录按其用途保留，不把它们误当成内部业务文档清理。

## 首次大型需求的临时 review 快照

仅当 `skill:align` 已识别出**全新的大型需求**且项目不存在现成需求文档时，在任务开始时建立一份临时需求快照。已有需求文档时直接使用，不创建替代副本。

把快照放在运行环境约定的临时目录，不放入项目文档体系，不提交、不发布，也不转成持久 spec。它只记录首次 review 所需的原始需求：目标、范围与非目标、验收标准，以及关键不可违背的业务约束；不记录实现方案、字段清单或调用顺序。

快照不作为设计、实现、调试或开发期决策的依据。初次功能开发完成后冻结它；调用方将确切的冻结版本与目标 diff 显式传给首次 review，reviewer 不自行扫描临时目录寻找文件。首次 review 完成后弃置该快照。

后续补充、二次修改、修复和普通增量开发只依据当次请求、当前代码、测试及仍有价值的持久文档推进；不得读取、引用、补写、校准或追溯此前的临时快照。

## 项目规则的极简承载

已有位置能承载就补在那里，不为一条规则新建治理体系，也不默认多层重复：

- 需要 Agent 高频遵守的稳定项目约定放 `CLAUDE.md` / `AGENTS.md`；
- 无法由代码表达且需要持续保留的跨模块决定或业务关系放现有 spec / 项目文档；
- 可稳定机械判断的约束交给 test、lint、type 或 CI；
- 必须在特定生命周期自动发生或即时反馈的动作才用 hook。

一个规则可以有说明层和执行层，但每层都应提供独立价值。

## 处理现有业务文档

- 删掉或收敛代码能够还原的字段、调用流程和局部规则；
- 只剩代码入口引用且没有独立业务信息的文档不保留；
- 文档中的局部业务 why 下沉到相邻代码注释；
- 保留代码无法充分表达、且需要跨开发周期维护的关键跨模块业务信息；
- 删除可能损失无法恢复的业务知识时，先指出疑点，不凭猜测迁移。

不要以整理业务知识为由扩大到无关重构，也不要把面向外部读者的交付文档误删成内部业务文档。
