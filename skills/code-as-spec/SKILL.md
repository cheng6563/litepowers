# 代码即核心业务文档

**代码流程、可观测性日志和就近注释共同构成核心业务文档。** 已实现的业务流程、规则、状态流转和约束以代码、SQL、schema 或配置为准；在关键状态变化、外部调用和失败分支记录足以排障的上下文与结果；无法从实现直接看出的业务语义、why 和特殊边界写在相邻注释里。日志不得包含敏感数据，注释不重复代码字面含义。

常规内部业务功能文档只做 **业务概念 / 流程 → 代码入口** 的索引，不复述字段、调用顺序或规则。入口可以是模块、类型、方法、schema、SQL 或配置，不必绑定到某一种代码结构。

## 什么时候保留独立文档

只在信息没有合适的代码载体时保留文档，例如：

- 稳定的项目级约定；
- 尚未实现、暂无代码承载的需求或决定；
- 需要跨模块导航的业务索引；
- 面向外部读者的使用说明、集成协议、运维手册或合规记录。

如果项目完全没有文档体系，**不要只为记录业务信息新建文档目录、模板或治理体系**；直接把信息留在对应代码和就近注释中。暂无代码时沿用项目现有的任务或沟通载体，除非用户明确要求建立文档。

## 项目规则的极简承载

已有位置能承载就补在那里，不为一条规则新建治理体系，也不默认多层重复：

- 需要 Agent 高频遵守的稳定项目约定放 `CLAUDE.md` / `AGENTS.md`；
- 暂无代码承载的决定或跨模块索引放现有 spec / 项目文档；
- 可稳定机械判断的约束交给 test、lint、type 或 CI；
- 必须在特定生命周期自动发生或即时反馈的动作才用 hook。

一个规则可以有说明层和执行层，但每层都应提供独立价值。

## 处理现有文档

- 代码能够还原的内容删掉或收敛成代码入口索引；
- 文档中的局部业务 why 下沉到相邻代码注释；
- 尚未代码化的信息暂留文档，实现后再下沉并收敛索引；
- 删除可能损失无法恢复的业务知识时，先指出疑点，不凭猜测迁移。

不要以整理业务知识为由扩大到无关重构，也不要把面向外部读者的交付文档误删成内部代码索引。
