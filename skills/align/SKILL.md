# 执行前对齐

用户提出新的、非简单开发需求或尚需定位修法的故障时先执行本 Skill；只读分析、review、用户明确限定的小改动，以及根因和执行方式均已确认的直接修复，直接进入相应任务。报错位置明确或已有修复猜测，不等于根因和执行方式已确认。当前请求与适用的全局、项目指令优先于本 Skill 的默认值；已确认的授权、验证和交付要求不因选择推进模式而清空。

当前任务推进中，以下情况沿用原模式，不重复询问推进模式：

- 当前任务执行过程中刚产生的测试、构建、CI、部署或运行失败；
- 对当前实现的局部修正、补漏或继续执行已授权的验证与交付动作。

续接须能核实当前任务及其原模式；同一项目或相似报错不代表同一任务。当前任务产生的失败视为原任务的证据：继承其 Scope、Evidence 和 Delivery；根因未知时直接转 `skill:systematic-debugging`，定位后回到原合同继续修复。只有失败暴露出新的业务目标、明显扩大影响范围、需要更换实现路线，或要求未授权的外部动作时才停下询问。

## 选择推进模式

先依靠现有上下文粗略判断任务难度，必要时只做确认范围所需的只读检查，不为选择模式启动 subagent。对适用本 Skill 的任务，按以下顺序选择模式：

1. 用户已明确选择模式，或能核实当前任务的原模式时，沿用该模式。
2. 尚未确定模式，但用户明确要求直接修改、自行决定或 AFK 时，采用快速推进。
3. 其余情况通过结构化交互询问并等待回答，不先开始实现或完整根因调查。

故障描述、“帮我修好”表达的是任务目标，不是免交互要求；已有测试、提交推送或部署约定只约束验证与交付，不代表选定推进模式。任务复杂度决定推荐项，不决定是否跳过提问。

提问提供以下选项：

- **快速推进**：内部确定最小合同，必要时先定位根因，再做最小修改；默认只做 diff 与目标文本检查，测试、构建和浏览器验证按明确要求执行；
- **对齐推进**：先扫描项目并确认执行合同，再开始修改。

疑似单点、报错集中且预计影响范围小的故障，推荐快速推进；涉及业务取舍或明显跨模块影响时，推荐对齐推进。标出推荐项并简述依据，等待回答。没有结构化交互工具时才使用普通文本提问。任何模式下，无法推断的高影响业务取舍或未授权外部动作仍须停在相应边界。

## 快速推进

内部形成最小执行合同后直接修改，不创建计划文档、持久 spec、ADR。默认由主线程实现；用户或项目明确安排的委派按 `skill:delegation` 执行。独立 review 只按本次已确认的选择执行。

普通细节按用户目标、现有代码和项目约定处理。若新发现会改变已确认的核心行为、完成标准、公开接口、数据结构、架构、外部副作用或明显扩大范围，停止相关动作并询问；用户离线时完成不受影响且已授权的部分，记录阻塞项。

默认仅完成本地修改与 diff、目标文本检查，不运行测试、构建或浏览器验证，不提交推送，不部署发版；已有明确要求与长期交付约定仍然执行。检查只能证明其覆盖的内容，未执行的验证如实标明。

## 对齐推进

先扫描相关代码、spec 和项目约定，再形成轻量执行合同：

- **Scope**：目标、非目标和可观察的完成标准；
- **Approach**：直接实现、先设计、定位根因或测试先行；
- **Evidence**：用哪些现有测试、构建、复现或其他证据判断结果；
- **Delivery**：是否本地测试、提交推送，以及 Web 项目是否发布测试环境并进行浏览器验证。

能从请求和项目事实可靠推断的直接采用，只询问会改变执行路线且无法确定的事项。使用结构化交互提供 2–4 个真实选项、说明影响并标出推荐项，然后等待回答；没有真实取舍时不凑选项。

Evidence 能由现有测试体系和项目约定确定时直接采用。非 Git 项目不询问提交推送；无远端不询问推送；没有已确认测试环境入口时不询问部署。生产部署或正式发版仅在用户明确要求时执行。

## review 与任务续接

在对齐推进的合同交互中，本次是否独立 review 尚未明确时，询问“开发完成后是否需要独立 review”，提供需要与不需要两个选择并等待回答；已明确选择时不重问。AFK 且未选择时不自动安排 review。

对齐推进已选择开发后独立 review 的，在开发前按 `skill:code-as-spec` 建立临时验收输入，并按该 Skill 维护到本次问题处置结束。快速推进中显式要求独立 review 时，直接提供当前需求与验收标准，不强制补建临时文档；未选择时不创建 review 文档、不自动安排 review。

review 的目标范围由调用方固定：实施前记录任务起点，完成后按 `skill:delegation` 委派独立审核，显式提供当前验收输入、审核目标与工作区变更或明确的 base/head；包含未跟踪的新文件时一并提供，不因已提交而漏审。原合同范围内的缺陷修复沿用已有授权；单独的只读 review 请求不附带修改权限，扩围或新增外部动作仍须确认。

新任务确定推进模式后，根因未知时转 `skill:systematic-debugging`；选择测试先行时转 `skill:tdd`。任务内失败沿用已确认模式直接调查。专项 Skill 返回后继续按原合同执行，不重复询问。

跨轮次或上下文恢复时，先恢复本次 Scope、Approach、Evidence、Delivery、review 选择和已完成状态，再继续下一步。优先使用现有任务清单或会话台账，不另建治理文档；无法核实的授权不按已获授权处理。

## 结果与后续

按当前输出约定报告结果、关键取舍、实际验证、未完成项和剩余风险；证据只陈述实际观察到的结果，不把写了测试或 reviewer 未报问题等同于验证通过。

存在会改变后续动作的未决事项时才给出下一步。AFK 任务在已授权交付终点停止，并集中报告阻塞项。
