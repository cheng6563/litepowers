# 系统化调试

恢复原始诉求与已确认上下文，明确失败动作、预期结果和受影响对象；责任归属随取证确定。

## 取证

1. 读取完整错误和上下文，复现问题；不能复现时收集能区分假设的证据。
2. 沿调用链或数据流找到最早偏离预期的位置。核对本次实际输入、对象、状态、时间和分支条件，以及接口或业务规则的成功含义、有效范围与计时起点。日志记录的执行事实还需核实是否符合业务期望。
3. 优先对照正常与异常场景从触发到业务结果的实际路径和关键差异，并确认正常场景确实达到预期；额外入口、重试或补偿可能掩盖共同缺陷。若正常场景也缺少拟认定为必要的步骤，先核实该步骤的必要性。
4. 一次验证一个具体根因假设，只改变一个变量；实验或修复失败后，先复核所选路径及其适用前提，再决定是否调整参数或更换输入。失败后撤销实验再提出新假设；连续三个假设失败时停止试改，重审证据、前提和架构。

根因判断须有适用于本次故障的证据支持，结论应解释故障和关键对照。运行行为用相关日志或复现结果核实；源码、配置或适用规则足以确定结论时可直接采用，未证实的环节标明证据缺口。用户补充或纠正后，保留有效证据、撤回失效推断并继续核查；与已确认记录冲突时，先核对所指对象、时间和业务节点，再更新结论；重提已排除假设须有新证据。

查询或连接失败时，明确证据缺口，改查已有日志、其他入口、本地源码或配置。把影响结论的疑点转成具体行动，在现有权限内持续取证，直到关键因果链闭合或有效路径均受阻。

## 结论与修复

先用业务语言说明失败及后果，再给已证实原因、处理方向和待验证事项；受阻时说明已尝试路径、缺失证据及最小解除条件。回复可简短，调查仍须查清因果。

修复方向须能恢复原业务效果，并推演已发现相关入口的遗漏、重复执行和状态变化。新增补偿或改走其他接口前，先查证其对当前对象、状态和目标的适用性；依据适用规则或同场景成功记录验证，缺少依据时先验证此前提。代码已有实现、请求已发出或单元测试通过，只能证明各自覆盖的行为。

诊断期间保持生产行为不变。只诊断任务交付根因、证据和必要修复方向；首次转入修复时由 `skill:align` 承接，交接原诉求、根因证据、建议与待定事项。

实施中的任务沿原需求、模式、验证和交付终点继续修复。测试失败对照修改前基线与旧测试排除依据：失修测试沿用排除结论，本次回归继续处理。
