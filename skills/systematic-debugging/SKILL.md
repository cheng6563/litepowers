# 系统化调试

先恢复原始诉求与已确认上下文，用业务动作说明哪里失败、应得到什么结果及受影响对象；用户使用的“接口问题”等称谓先按其描述的故障理解，责任归属随取证确定。用户追问或纠正时，更新受影响的判断和取证动作，沿原任务继续查清尚未闭合的因果链。

## 取证与假设

1. 读取完整错误和相关上下文，复现问题；不能复现时先收集能区分假设的证据。
2. 沿调用链或数据流回溯，从症状追到最早偏离预期的位置。日志中的过滤、跳过或调用成功先作为实际执行事实，再核实该条件是否符合业务期望。例如接收人被权限过滤后，还需核实该权限实际控制的功能、目标角色的职责及相关调用方。前一步成功、后一步拒绝时，对照本次实际请求、响应或回调中的对象标识、状态与时间，再核对对应接口或业务规则的成功含义、有效范围和计时起点。
3. 用实际记录验证一个具体根因假设，一次只改变一个变量。源码疑点须核对本次输入、分支条件和运行记录是否命中；假设失败时撤销实验，再提出新假设。
4. 用户提供正常场景或其他对照时，比较两者从触发到最终业务效果的关键差异，核实对照是否达到预期。额外入口、重试或补偿可能掩盖共同缺陷；只查到调用成功仍需确认对象、结果及副作用。

查询或连接失败时，判断失败覆盖的证据范围，再尝试已有日志、其他查询入口、本地源码或配置等可用来源。连续三个假设失败时停止试改，重审证据、前提和架构，再选择能减少关键不确定性的调查路径。

## 根因与修复方向

根因结论须能解释本次故障及已提供的关键对照，并区分已证实的因果关系与待验证事项。定位到报错环节后，继续核实拒绝条件为什么在本次成立；本地代码疑点和三方错误文字均须与本次运行记录、适用规则对上，才能支持根因与责任判断。

把会改变结论的疑点转成具体取证动作，优先使用现有工具和权限执行。只有诊断范围内的关键因果链已闭合，或有效取证路径均受阻时才交付；受阻时说明已尝试路径、缺失证据及最小解除条件。用户纠正后，保留仍成立的证据，撤回失效推断并执行新的核查；重新提出已排除假设须有新证据。

提出修复方向前，核对它能否恢复原诉求的业务效果，并沿本次已发现的相关入口推演其影响，例如遗漏、重复执行和状态变化。

汇报先用大白话说明哪里失败及业务后果，再给已证实原因和处理方向；把尚未确定的责任限定到具体缺口。用户要求简短时压缩说明，调查深度仍以查清本次因果链为准。

本 Skill 在诊断期间不修改生产行为。只诊断任务交付根因、证据和必要修复方向。

从只读诊断转入首次修复时，转 `skill:align` 按其入口判断并承接实施，交接原诉求、根因证据、建议方向和待定事项。已在实施中的任务沿用需求记录、原模式、有效验证和交付终点继续修复。测试失败先对照修改前基线与旧测试排除依据，确认失修的旧测试沿用排除结论，本次回归继续处理；不因定位完成而结束或重新询问推进方式。
